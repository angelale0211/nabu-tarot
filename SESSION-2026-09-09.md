# Handover — 2026-09-09, the session that got Play Billing actually working

For the other Claude session. Read section 5 first: there is uncommitted work
from more than one session in the tree, and one hazard that would ship a broken
release if committed as it stands.

Companion document: **`BILLING-REPORTS-2026-09-09.md`** — three testers have
reported buying failing since all this landed. That file is the diagnosis and
the toolkit. The short version is at the end of section 4 here.

---

## 1. The headline

**Play Billing now works end to end, proved with a real purchase**, not a stub.
Client → worker → Google → ledger → account → back to the client. The
`purchases/` collection has its first row ever.

It had never worked. Four separate failures were stacked on top of each other,
and **every one of them was silent** — the badge said green, the code read
correctly, and the app could only say "no response from Google Play".

| # | What was actually wrong | Fixed by |
|---|---|---|
| 1 | `_headers` served `Permissions-Policy: payment=()`, which denies the payment policy to **every** origin including our own. The Digital Goods API is gated on it, so `getDigitalGoodsService()` threw `NotAllowedError` before a line of Play code ran. Written 2026-09-07, two days before billing merged. | `payment=(self)`, plus a suite check |
| 2 | The worker deploy step ended `exit 0` when `CLOUDFLARE_API_TOKEN` was missing. Runs went **green while deploying nothing**, for two days. The handover cited those green runs as proof the worker was fine. | fails loudly now (`bbc24da`) |
| 3 | `wrangler` is `^4.0.0`, so CI installs the newest 4.x; a release raised its floor to **Node 22** while the workflow pinned Node 20. Install/Types/Tests all passed, only Deploy died, and a job log needs **admin rights even on a public repo**. So the four subscription ids from `effa39f` were never deployed and every subscription purchase answered `unknown product`. | `node-version: '22'` (`9faab3d`) |
| 4 | `PLAY_SERVICE_ACCOUNT` existed as a secret but the worker could not use it, so `serviceToken()` threw and **all eight** skus answered `check failed` — including with a dummy token, which is what gave it away. | owner rotated the secret |

Nothing in the billing code itself was wrong. Every fix was in the seams:
config, CI, deployment, credentials — exactly where nothing was watching.

**Observability → Logs is now ON and declared in `worker/wrangler.toml`**, so a
refused purchase records its real exception instead of only the generic
`check failed` the phone sees. Left in the dashboard alone it would have been
switched off by the next `wrangler deploy`.

## 2. Bugs found by an adversarial sweep, and fixed

A workflow swept the repo for the same *class* of defect — silent failures — and
18 findings survived adversarial verification. These four were fixed. Each has
a test that was **proved to fail without the fix**.

- **`src/billing.js` / `src/store.js`** — a purchase Play had completed was
  reported to the buyer as "Mua chưa thành công". `buy()` throws `offline` only
  *after* `res.complete('success')` and a real token: Play has charged, the
  token is on the pending list, `restore()` finishes it. It now shows the
  pending wording. The owner personally hit this. (`6c7f3b8`)
- **`worker/src/refunds.ts`** — `removeAccess()` answered `[]` for *every*
  read failure, and `markVoided()` ran anyway, so one blip left a refunded
  buyer holding the course for ever with the ledger saying it was handled.
  404 now means "no account"; everything else throws and retries. (`cb39b70`)
- **`worker/src/refunds.ts`** — a refund deleted the whole access key, taking
  away a course the person had also bought a second time or paid for by bank
  transfer. It now computes a floor from the surviving ledger rows plus
  `granted`, and **lowers** rather than deletes. `noteGranted` was widened to
  record course keys for this; `recompute` deliberately was **not**. (`bd4c1f0`)
- **`src/store.js`** — subscribing to Pro while holding Plus never passed
  `oldKey`, so Play started a **second concurrent subscription** beside the
  first. Both renew. (`9a60229`)

**Not yet fixed, still on the list** (all adversarially confirmed):

- `firestore.rules` `/people/{uid}` — `allow write` covers delete, and on a
  delete `request.resource` is null, so `shorterThan()` errors and **every
  profile deletion is denied**. Also an App Store blocker: in-app account
  deletion is mandatory on iOS. *A fix is written in the working tree,
  uncommitted, and needs `npx firebase-tools deploy --only firestore:rules`.*
- `firestore.rules` `taken/{slot}` — the update rule checks the *incoming*
  bookingId belongs to the caller, never the row being overwritten, so anyone
  with a booking can take someone else's hour. *Fix also written, uncommitted.*
- `src/backend.js` `takenSlots()` — returns `{}` on any failure, so every hour
  shows free on a slow connection. *Unfinished fix is in `stash@{0}`.*
- `worker/wrangler.toml` — `[[kv_namespaces]]` is commented out, so `env.KV` is
  undefined and `allow()` returns OK for everyone: **rate limiting is inert.**
- Listener leaks in `me.js` / `admin.js`; unguarded `$('#welbday').value` after
  an await in `welcome.js:105`; `config.js` `bookingEndpoint: ''` makes
  `notifyBooking()` a no-op so calendar invitations are never sent;
  `build.py:67`'s inline-handler assertion can never match, so it has never
  checked anything.

## 4. The bundle rebuild that was about to happen

The owner approved a **versionCode 3** rebuild to fix the last visible thing:
a strip of the system navigation bar showing lavender under the cream app bar.

That is **not a layout bug** — no CSS reaches those pixels. The band is the
Android system bar, painted with the manifest's `theme_color` (`#EFE9FA`),
which is exactly the colour measured in the screenshot.

The build is a copy of the versionCode 2 request at
`nabu-tarot-keys/pkg-billing-pkg-2026-09-08/request-without-secrets.json`
(passwords are in `signing-key-info.txt` beside it), changing only:

    navigationColor            #EFE9FA -> #FFF9FA   (the app's --surface)
    navigationColorDark        #241A45 -> #312559
    navigationDividerColor     #EFE9FA -> #FFF9FA
    appVersionCode / appVersion    2 / 1.0.1 -> 3 / 1.0.2

Everything else must stay identical — `features.playBilling.enabled`,
`minSdkVersion 23`, host `nabutarot.com`, `signingMode: mine` with the
`my-key-alias` keystore (B7:56, the upload key Play names).

**Before doing it, read `BILLING-REPORTS-2026-09-09.md`.** Three testers now
report buying failing, and the most likely cause is that they are still on
**versionCode 1**: alpha served it until it was promoted this afternoon, and
versionCode 1 has no `com.android.vending.BILLING` and no `PaymentActivity` at
all, so the Digital Goods API does not exist inside it. The owner's emulator
was never affected because it installs from *internal*, which has had
versionCode 2 throughout. Ask a tester whether Play offers an Update before
building anything.

## 5. Hazards in the working tree, right now

**Version markers disagree.** `sw.js` says `nabu-tarot-v210`;
`src/main.js` and `index.html` say `v209`. Committing that ships a service
worker that never matches its page — phones pinned to a stale version,
silently, with nothing in git looking wrong. Reconcile before any build.

**Two stashes, from more than one session:**

    stash@{0}  src/backend.js  src/book.js  src/main.js  src/store.js  src/strings.js
    stash@{1}  src/billing.js

`stash@{0}` contains an unfinished `takenSlots()` fix (see section 2). The
`store.js`, `strings.js` and `billing.js` changes in them are **not mine** and
I do not know what they are for. Restore deliberately; do not assume either is
disposable.

**Uncommitted and not in a stash:** the two `firestore.rules` fixes from
section 2. A copy is kept outside the repo at
`…/scratchpad/firestore.rules.SAFE` in case a third stash takes them.
